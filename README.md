# Board

A personal command center that runs locally. No backend, no build step, no dependencies: plain HTML, CSS and JavaScript modules. Your data is stored as JSON files in a folder you choose.

Sections (v1):

- **Todos**: personal and per-project lists. Type `buy milk #home` to file a todo under a project. Tasks are sorted by status (in progress first, completed last); click a column title to sort by it, and a third click returns to your own order. Drag the grip to reorder, within a status while sorted by status. Paste several lines to create a todo with a description. Click the description icon to read or edit it. Paste or drop images on a task (or pick them with Add image in its details): they are kept in `tasks/` in the data folder, and a Dev session on the task hands them to claude.
- **Calendar**: the events of one or more Google accounts side by side, by day, week or month, coloured by calendar, with open task deadlines on their days. Day and week are a time grid as in Google Calendar: events placed by the hour and side by side when they overlap, all-day and multi-day events in a strip above, and a line at the current time; a small month beside it jumps to any day. Show or hide calendars from a searchable list of each account (with its Google picture) and its calendars, or filter by project or project label when a calendar has one (Settings → Google Calendar). Open an event for its time, place, notes and a link to Google, or turn it into a task in its calendar's project. A project and project label set on an account apply to each of its calendars without their own. Each account signs in on its own for about an hour. Each account connects once: its sign-in is kept in `google.json` in the data folder and renewed before it expires, so it stays connected in every browser profile that opens the folder. Events are cached in `google.json` too: a reload shows the last read at once, and Google is asked again once the cache is 10 minutes old, or with Refresh. Home shows the next two days.
- **Projects**: quick-add by name, or a detailed form for color, description, and GitHub links (one org, several repos, or none). A project's **Local folder** (its path on this machine) is where the Dev section opens terminals for it; Browse finds it in a folder list starting at ~/Documents (needs the runner, see Dev). A project's **Profile** is a short saved text on what it is, its stack, how to work on it, its recent focus and what its website says: Build profile reads the local folder's README, AGENTS.md, CLAUDE.md, package.json and last 30 commits (through the runner), the repos on GitHub, and the website plus any extra URLs, then asks the model once (capped at about 6,000 words of input). A source that cannot be read is listed under Unknowns. The text can be edited by hand; Refresh asks before replacing edits. Tidy, Plan my day and Triage send the profiles of the projects in their input as context.
- **Kitchen**: recipe ideas, recipes you are testing, and final recipes. Log each iteration with notes and a rating. Drop a photo of a recipe, handwritten or printed (up to 4 pages), and the model set for Read recipe photos rewrites it as a recipe; the photo is kept in `recipes/` in the data folder.
- **Money**: rough income and expenses per month, with totals and a per-category breakdown.
- **Tools**: checks on each project's website: is it reachable (open a site for its response times, other checks and a log of warnings and errors), when its SSL certificate and domain expire, every DNS record it has (with SPF, DMARC and DKIM for mail), what its crawl files say (robots.txt, sitemap, llms.txt, security.txt, ads.txt, the web app manifest, app links and more, each previewed with a format check), and how a shared link to it looks, with a task for any tag that is missing or could be better. **Provider status** follows the status pages of the services you rely on (GitHub, Vercel, Cloudflare, OpenRouter, and any other Statuspage or Datadog page), with open incidents, maintenance and the last 30 days. **Contracts** reads and writes the smart contracts saved in Settings: every view function can be called with typed inputs (arrays and tuples as JSON) and shows its decoded answer, **Read all** reads the ones without inputs, and every other function is sent as a transaction through your browser wallet once you press **Connect wallet** (nothing asks the wallet before that; with several wallet extensions installed, such as MetaMask, Rabby, Coinbase Wallet or Brave Wallet, pick one from the list), which switches to the contract's chain and asks before signing; the board then waits for it to land.
- **Summary** (the first view of the **DeFi** tab): total liquidity across the other views (wallet balances, LP positions, unclaimed fees, and Aave supplied less borrowed) with each one's share, warnings for Aave accounts close to liquidation and LP positions out of range, the fees collected over 30 days, and the main lines of Wallets, LP Positions and Lending / Borrowing, each with a link to open it. **Refresh all** reads them all again. It reads nothing of its own.
- **Liquidity Pools** (the **DeFi** tab, with **LP Positions** and **LP Fees Collected** views): Uniswap v3 and v4 positions of the wallets you add in Settings → Wallets, on Ethereum, Base, Arbitrum One, Optimism, Polygon, BNB Chain, Avalanche, Unichain, Robinhood Chain and ZKsync Era (v3 only, as Uniswap has no v4 there): range, value, unclaimed fees, fee APR and token split, sorted by value, unclaimed fees, fee APR, movement, newest or oldest. In the list view, every column header sorts by that column; click again to flip the order. Fee APR is read over the window picked beside Sort (15 min, 1 h, 3 h, 6 h, 24 h, 7 d or 30 d): every swap in the pool that ended inside the position's range pays it the fee times its share of the liquidity, as a yearly rate of its value. It is an estimate. Public nodes keep about a day of swap history, so the board also saves each position's earnings per hour, and the 7 and 30 day windows fill in as long as the board is opened about once a day. A window that is only partly covered shows the time it covers next to the rate. Where swaps cannot be read, fee APR counts the fees earned since the board first read the position, and shows after an hour. **Movement**, on each card and in the list, is the change in fee APR from the window before the one picked (the 24 h before the last 24 h, for example), in percentage points, shown once both windows are at least half covered. The **⇄** button beside a price range shows it in the pair's other token; the choice is saved per pair and used wherever that pair shows. Click a card, a row or a position in Fees Collected, open or closed, to open its detail: the range on a wider price scale with where the price sits, the room to each edge and the range width; holdings and unclaimed fees per token; fees earned and the fee APR they make over the last 24 h, 7 and 30 days from the saved hours, and per day; its collections; and its wallet, pool, token addresses (with block explorer links), liquidity and collect search. A position whose wallet was removed shows its last saved read. Read-only: only public addresses are used. v4 positions cannot be listed with a call, so the board finds them by searching each wallet's history on the chain, and remembers how far it got. Most public nodes keep only recent history, so set a node that keeps full history, or use **Add position** on the tab: paste a position link from app.uniswap.org (its chain and version are read from the link, for example `/positions/v3/base/556505`), or type its number and pick its chain and version. That also adds a v3 position held by an address that is not in your wallets. Each chain shows as soon as it is read. When a chain cannot be read, its last good read is shown and marked as outdated. Positions your wallets still hold but have emptied (no liquidity, no unclaimed fees) show under the **Closed** filter, left out of the totals. **LP Fees Collected** logs each collection, read from the collect transaction itself: the tokens it paid the wallet, less any liquidity removed in it (for v4, worked out at the pool's price just before), at the token prices of that day. The native coin leaves no token transfer, so its part is what the wallet gained in it, plus the gas it paid, or the amount Etherscan traced. Collects are found three ways, and the surest reading of each is kept: from the node, v3 positions' own events and v4's pool manager events, which read new blocks on every load and walk back toward each position's opening while the node keeps the blocks; and, with an optional Etherscan API key in Settings → Blockchains, each wallet's transactions to the Uniswap position managers, back to its first one. Etherscan only logs positions the board shows, as a burned position no longer says what its tokens are. Between two reads, a drop in a position's unclaimed fees is logged too, as a floor, and gives way to a reading of the same collect from the chain. You can also log a collection by hand or remove one. It shows the total collected, the average per day, week, month and year over all time, 30 days, 90 days or a year, and a chart by day, week or month whose bars show their total, count and top positions on hover, tap or arrow keys. Below the chart: an **Outlook** row (the range against the one before it, month-end and year-end estimates at the last 30 days' pace, the days to the next round total, the time since the last collect with the usual gap, and the average and largest collect); a **running total** with a dashed estimate ahead at the range's pace; the **pace per day** as 7-day and 30-day rolling averages, saying whether fees are speeding up or slowing down; **where fees came from** by position, chain or source, with each one's share; and a calendar of the **last 26 weeks**, one square per day, shaded by the fees collected, with the weekday that brings the most. They follow the chain, token and source filters. The token filter is searchable and shows each token's logo; each position in the log has a dot for open (green in range, amber out of range), closed (grey) or no longer read (hollow). **Search coverage** starts collapsed to a one-line recap and opens to say how sure the log is to hold every collect, for all chains and per chain: the share of positions, open and closed, whose search reached the transaction that opened them, or whose wallet Etherscan has read in full, with partial credit for the blocks searched back so far. Each load searches a step further back. With several nodes on a chain, its positions are searched side by side, one per node, and a position searches several block ranges at once when there are more nodes than positions, so each load reaches further; a line per position says what is being searched. **Search further** beside a chain runs one more step for that chain right away. **AI insights**, above the positions, counts how many are in range, out of range (with the value sitting idle) and near an edge, and with an OpenRouter key asks the model set for Pool insights in Settings to read them: a short summary, then one action per position (keep, watch, re-center, widen, narrow, collect fees or withdraw) with the reason and, where it fits, a suggested range. Prices are read and shown in the base each pair is shown in (see **⇄**). The last 5 reads are saved with their date and time and open again from tabs, and each can be filtered by action, in or out of range, and chain. It reads only the numbers the board shows, and is not financial advice.
- **Wallets** (in the **DeFi** tab): what each wallet in Settings → Wallets holds on the chains Liquidity Pools reads: its native coin and every token on the chain's Uniswap token list, read in a few batched calls through Multicall3, with prices from DefiLlama. Shows the total, the value by token, by chain and by wallet, and a sortable table filtered by wallet and chain. Hide a token from its row; **Tokens** adds a token the list does not carry by its contract address, and lists the added and hidden ones. Each chain shows as soon as it is read; a chain that fails keeps showing its last read. Read-only.
- **Lending / Borrowing** (in the **DeFi** tab): the Aave v3 positions of every wallet in Settings → Wallets, on the chains read that have Aave (Ethereum, Base, Arbitrum One, Optimism, Polygon, BNB Chain, Avalanche and ZKsync Era). One card per wallet and chain, riskiest first: the health factor (green, amber under 1.5, red under 1.1, where liquidation starts below 1), what is supplied and borrowed with each asset's APY and whether it counts as collateral, the net value and net APY, and how much of the borrow limit is used. Totals across all of them, the lowest health factor, and a warning for any account under 1.1. Filter by wallet and chain, and switch between cards and a list with one row per account. Values use Aave's own price oracle. Read-only.
- **Dev**: a small IDE for this machine, Cursor style. Pick a workspace (the board's folder, your home folder, or a project's local folder): its files show as a tree on the left (without `.git`, `node_modules` and build caches), and a file opens read-only in a tab, with line numbers and syntax colours for JavaScript, TypeScript, JSON, CSS, HTML, Markdown, Python, Shell, YAML, TOML, SQL, Solidity, Rust, Go, C, Java and Swift (files up to 1 MB). Terminals sit below: each runs commands in a real terminal (a pseudo-terminal from the system's `script` tool), so colours show (adapted to the light or dark theme, so a program's own colours stay readable) and interactive programs work, including the Claude CLI, prompts and full-screen tools like `vi`: click the output and type, and your keys go to the program. `cd` moves the terminal, `clear` or Ctrl+L empties it, a web link it prints (plain or OSC 8) opens in a new tab when clicked, Up and Down walk the saved commands, and Stop ends the command and anything it started. Hover a folder in the tree to open a terminal there. Paste or drop an image on a running terminal and its path is typed in, so claude attaches it (the runner saves a copy in its state folder; images not used for 30 days are deleted). Icons at the top of the side panel switch between Files, **Search**, **Source control** (with a badge counting changed files) and **Worktrees**, as in VS Code or Cursor; each panel has a title with its actions beside it, and the Files tree hides the worktrees claude makes in `.claude/worktrees`. Search finds text in the workspace's files as you type (through `git grep`, so files git ignores, binary files and claude's worktrees are left out), with toggles for match case, whole word and regular expression, and, under the `…` button, files to include and exclude (comma-separated globs such as `*.js, src/`). Results are grouped by file; a match opens the file at its line. It shows the first 2,000 matches. Source control leaves out the worktrees claude makes in `.claude/worktrees`, and Commit all does not stage them. It shows the workspace's branch (click it to switch to another or create one), pull and push with how many commits each way (Publish for a branch with no upstream, plus fetch), a commit box (Cmd/Ctrl+Enter commits; with nothing staged, Commit all stages every change first), and the merge conflicts, staged changes and changes, each file with buttons to stage, unstage, discard (after a confirmation) or open it. A file opens its diff in an editor tab, and a recent commit opens what it changed. The file tree colours changed files with git's letter (M, U, A, D) and marks the folders holding them. Source control reads the repository again every few seconds while Dev is drawn, and after each command ends. Pull only fast-forwards, and git never asks for a password here: a push that needs one fails and says so. Worktrees lists every git worktree of the workspace's repository but the main checkout, each with a dot: green while claude (its lock) or a terminal's command runs in it, amber while an open task or terminal points at it, grey when nothing uses it. They are grouped under In use, Held and Not in use (each group folds), and under each name are the task it was made for, its branch and what uses it. Each can be removed, or all the unused ones, or all of them (after a confirmation); git keeps any with changes or untracked files and says why beside it, and branches are kept. Up to 12 terminals run side by side (`TERMINAL_MAX` raises the limit). Terminals outlive the page: reloading or closing it leaves their commands running, and when Dev opens again every terminal is back with its whole output (the last 2 MB of each). The runner, not the browser, keeps the list of open terminals, so another browser on this machine (or one whose site data was cleared) opens the same terminals. With more than one terminal open, the address names the one shown (`#/dev?term=2`), so a refresh or a bookmark opens it. The runner keeps that output in a folder of the system's temp folder (`TERMINAL_STATE` picks another), so it also survives a runner restart, though a command running then is stopped; terminals not opened for 30 days are deleted. Closing a terminal's tab stops its command and deletes its output. Needs `bun start` (or `bun dev`), which starts the runner (`tools/terminal.js`); it listens on 127.0.0.1 only, answers only pages served from this machine, and reads your files without ever writing one, except through the git actions you click in Source control and Worktrees and the images you hand it. macOS and Linux; on Windows commands run without a terminal.
- **Cron**: recurring flows, drawn as a chain of steps like a workflow canvas. A schedule (every few minutes or hours within optional active hours, daily, on chosen days of the week such as weekdays, or on chosen days of the month and months, each at one or more times of day, or a custom cron expression such as `*/15 9-17 * * mon-fri` with a preview of its next runs) starts the chain: gather data from the board (open, overdue, high priority or soon-due tasks, one project or an overview of all, spending this or last month, income, calendar events today or in the next 7 days, unread Inbox mail, unread notifications, site check problems, liquidity pool positions, a web page such as a project's website, a path on it like `/blog` or any full link, along with up to 10 pages of the same site it links to, picked across its sections, such as a blog's latest posts, the flow's own past outputs, another flow's latest output, or fixed text; the source list is searchable, one data step can read several sources, each under a heading with an optional label), ask an AI model with a prompt that uses `{{input}}`, then create a task or post a notification, or start work in Dev: a "Run in Dev" step hands a Dev prompt to the project's Dev command, a preset from Settings → Dev environment or a custom command (or runs a plain shell command) in a new Dev terminal in a project's local folder, without leaving the page, and the task made earlier in the run goes with it, as from its Dev button, so the PRs claude opens are added to it. A data step can add to the previous one's output instead of replacing it, so one prompt can hold a website, its blog and earlier drafts. Templates cover website content ideas, blog post drafts, and X and LinkedIn posts for a project or a personal account; they write drafts as tasks and never post anything. "Blog post as a PR" drafts a post, adds it as a task, then has claude add it to the project's repository and open a pull request. A "Stop if" step ends the run quietly, for example when the data step found nothing. A "Refresh project profile" step rebuilds a project's profile as Refresh does in Projects (its output is the new profile), and keeps one edited by hand unless told otherwise, stopping the run quietly; the "Refresh project profile" template does it every Monday. "Test run" tries the whole flow as it will run: it makes its tasks and starts its Dev terminals, tied together as from a task's Dev button, but sends no notification, leaves the schedule alone and is not read back as the flow's history. A "Run in Dev" step with steps after it waits for its terminal (until it ends, or claude is done and waits), then passes on what it did: `{{input}}` as text, and its parts as `{{stepN.branch}}`, `{{stepN.commit}}`, `{{stepN.files}}`, `{{stepN.pr.url}}` and `{{stepN.output}}`, so a second Run in Dev, an AI step or a notification can build on it; the PR it opened is added to the run's task. A "Run in Dev" step can also be tested "in a terminal": it starts for real (with no task) and its output shows under the step as it runs. Each run's Dev terminal can be read later under that step in the run, from what the runner keeps until the terminal is closed in Dev, and "Open in Dev" opens it to type in it. Each step can also be tested on its own, as in n8n: the steps before it that have no test data run first, and its input and output show as JSON trees. Any step can read every earlier step's output as `{{step2}}`, and a path reads into JSON output or what a step made (`{{step2.items[0].title}}`); steps keep their references when they move. `{{project}}` is the project's name, and its parts read with a path: `{{project.website}}`, `{{project.domain}}`, `{{project.repo}}` (the first GitHub repo, `owner/repo`), `{{project.repoUrl}}`, `{{project.repos}}`, `{{project.org}}`, `{{project.directory}}` (its local folder) and `{{project.description}}`; it is the step's or source's own project, else the flow's, and a web page source's address and fixed text take variables too. Fields that take variables list them under them, and a click on a variable or on a key of the test input puts it at the cursor. Each step's output from the last run is shown beside it. A flow has one project, chosen once next to its name: data, task and Dev steps use it unless a step chooses another, and the flow list can be filtered by project. Three tabs: Flows (the editor; flows can be paused from the list, duplicated or saved as a template), Runs (every flow's history, shown while a run goes, each with a status dot, its duration and links to what it made: the task, the Dev terminal with what it is doing, the PR and the branch; filtered by running, failed, stopped or test runs). A task a flow made has a blue Cron button that opens the run that made it and Templates. Flows run only while the board is open; a run missed while it was closed happens once when you open it.
- **Settings**: the gear at the top right. **Blockchains** lists the chains the board reads, with the nodes and block explorers of each, one field per address with a button to add another (built-in chains start with several public nodes and their usual explorer; empty the fields to go back to them), whether Liquidity Pools reads it, and a **Test** that asks each node for its chain ID and latest block and names any that fail. With several nodes, reads go to the node answering fastest, spread across them, and a node that fails or stops answering is set aside for a minute while the others take its calls. Links open in the first explorer listed. Add any other EVM chain by its nodes (its ID is read from them) and, optionally, its block explorers. The optional **Etherscan API key** sits here too: Smart contracts fetches verified ABIs and contract transactions with it, and LP Fees Collected reads each wallet's collects. **Smart contracts** saves contracts by chain, address and ABI (pasted, or fetched from Etherscan when it is verified), optionally tied to a project. **Prompts** shows the system prompt of every AI feature; edit one to change how that feature answers, or add a prompt sent with every AI call. **Dev environment** lists every project with its local folder (Browse finds it) and the command a task's Dev button runs, as on the project's page. Command presets above the list name a command once; a project picks one instead of pasting the same command, and editing a preset changes it for every project that uses it. Removing a preset leaves its command on those projects as their own.
- **Monitoring**: AI usage (cost, calls and tokens by model and task), GitHub activity, web analytics, search and smart contracts (transactions with an Etherscan key, and the events read from the node, decoded by the ABI, with the methods called, the events emitted and the latest of each). Hover or tap a bar, or focus a chart and use the arrow keys, to read its values. Select a recent AI call to see the messages sent, the full reply and the details OpenRouter returned. **Dev sessions**, under AI usage, shows what the claude sessions started from tasks used: cost, tokens and time worked, by model and provider (Anthropic, Amazon Bedrock or Google Vertex AI, from the model id) and by task, with the effort used. The cost is split into what the Claude plan includes and what is billed as extra: replies after the plan's limit switched to extra usage (Claude Code notes `isUsingOverage` in the transcript when it does), every session when the machine's Claude login (`~/.claude.json`) has no Claude plan, and Bedrock or Vertex models. The split follows each model's tokens, as Claude Code gives the cost only by model.
- **Inbox**: the emails every project sends and receives through Resend and Gmail, laid out like a mail client. Received mail lands in the Inbox; Sent, Starred, Archive and All mail are folders beside it. New mail is unread until opened, and the Home page counts it. Star or archive an email (with undo), filter by project, delivery status (delivered, bounced, opened…) and emails that have a task, or search all mail by subject and address. Open an email to read it with the rest of its conversation, or turn it into a task in its project. Each project has its own Resend key in Settings; projects that share an account can share a key, and their emails are told apart by the project website's domain. The runners read new mail in the background (Gmail every 2 minutes, Resend every 5) and Refresh asks them to read now, so the Inbox needs `bun start` running (see Runners). Gmail accounts can be added too (Settings → Gmail), each with an optional project and project label to filter by, read-only with the same Google OAuth Client ID as Calendar; each account signs in on its own for about an hour, and a Mailbox filter shows one account at a time.
- **Notifications**: the bell in the top bar lists deadlines, automated tasks, site checks, provider outages and Telegram messages.

Tasks have a deadline. The lists **Today**, **To Organize** and **Automated** gather what is due, what arrived without a project or deadline (for example from Telegram), and what the board created by itself. Press Cmd/Ctrl+K or `/` to search, jump, or capture something:

- a task: `fix the footer #atlas !high friday`
- a Money entry: `-42.50 groceries weekly shop` is an expense, `+4200 salary` is income, both dated today
- a recipe: paste a link to import it into Kitchen

The last row, **See all results**, opens the search on its own page: **All** shows the first matches of each kind, and a tab per kind (Tasks, Projects, Recipes, Sections, Settings) shows every match.

The search box in Tasks filters the list as you type. Words match the title, description, category and project; `#atlas` keeps a project (`#personal` for none), `!high` a priority, `is:doing` a status (`is:done` looks in completed tasks too), `cat:design` a category, and `due:today`, `due:late`, `due:week` or `due:none` a deadline. Search page results for tasks open in Tasks with the same filter.

A task's checkbox selects it; the check button next to its status marks it done. Shift+click selects a range. With tasks selected, a bar sets their status, priority, project, category or deadline at once, copies them as a Markdown checklist, or deletes them. The copy button on a task copies just that one. The terminal button (or Dev in the bar, for the selected tasks) opens a new Dev terminal that runs `claude --dangerously-skip-permissions --worktree -- <prompt>` with the tasks, in the project's local folder when it has one (a project's Dev command, its own or a preset picked in Settings → Dev environment, replaces that command), and moves open tasks to In progress. A task's images go along: the runner saves a copy of each in its state folder and the prompt lists their paths, so claude reads them. While that terminal runs, every github.com issue or pull request link it prints (for example when claude opens a PR or an issue) is added to the tasks, when the link's repo is one of the project's repos (any repo for a project with none). When claude is done, the tasks still In progress move to In Review: once it prints a pull request link, when it ends its turn and waits for you (its terminal has printed nothing for a few seconds), or when it quits on its own (exit 0). The terminal keeps its tasks through a reload. The task remembers its terminal: its terminal button then takes the colour of what the terminal is doing (blue while claude works, amber while it waits for you, green when it finished, red when it ended with an error, grey when stopped) and opens that terminal in Dev, where a back arrow beside its tabs returns to the page you came from. Shift+click starts a new session instead. The colour comes from the command runner, asked every few seconds once Tasks has been opened. The worktree claude makes is named after the task (a `--worktree` or `-w` with no name in the command gets one, such as `fix-the-login-a1b2c3`), and the task remembers it: once every task handed to that session is completed, from anywhere on the board, the runner stops the session and removes the worktree with `git worktree remove` (its branch is kept). git refuses a worktree with uncommitted changes or untracked files; that one is kept, a toast says why, and it is tried again when the task is reopened and completed again. While the board is open, the runner reads what that session used from Claude Code's transcripts (in `~/.claude/projects`, found by the worktree's name, also after Claude moves them once the worktree is removed): the models and their provider, the effort, the tokens (input, cache and output), the cost and the time worked, as Claude Code counts them (the cost once claude quits). It shows in the task's details, beside its terminal in Dev, and in Monitoring. Only sessions with a board-named worktree are read. A task's issues and PRs show as links beside its title; the link button in its actions lists them, unlinks one, creates an issue, or links an existing issue or PR.

Outside a field, `g` then a letter jumps to a section (`g t` for Tasks, `g m` for Money), `n` starts a new task, and `?` lists every shortcut.

Deleting a task, a Money entry, a bill, a recipe or a recipe iteration shows **Undo** for a few seconds.

Settings → Labels lists the task statuses, the task categories, the project labels and the Money categories, each in its own section (the Labels button in Tasks opens it). Rename one, change its colour, drag it into another order (every picker and filter that lists them follows it, and Sort A–Z puts a list back in order), or delete it; deleting one that is in use first moves its tasks, projects, or its entries, recurring items and budget, to another category or label. The seven task statuses are fixed, so they can be renamed, recoloured, reordered and hidden from the pickers, but not deleted.

## Run it

Browsers only allow the folder picker on a secure origin, so serve the folder locally:

```sh
bun start
# or, without Bun
node tools/start.js
```

This starts the board's static server, the Dev section's command runner and the runners (see below) together, in one process; Ctrl+C stops them all. Each prints its own lines in the terminal, prefixed with its name (`board`, `terminal`, `worker`): the board logs page loads and failed requests, and the runners one line per job run. Then open `http://localhost:8000` in **Chrome or Edge**. `PORT=<port>` picks another port for the board, and `TERMINAL_PORT` for the runner (8419; set the same address on the Dev page). To run only one part, use `bun run serve` or `bun run terminal`. `package.json` only holds these scripts: there is nothing to install. The File System Access API is not available in Firefox or Safari.

`tools/serve.js` has no dependencies and marks every file `no-cache`, so the browser always runs the code you just edited. Any other static server works too, but `python3 -m http.server` sends no cache headers, so Chrome reuses the modules it cached earlier and keeps running the old code after a reload: with that server, hard reload the page (Cmd+Shift+R) after every change.

While working on the board itself, run `bun dev` instead of `bun start`: it starts the same services and restarts them all when a file under `tools/` changes. The page's own files (`index.html`, `js/`, `css/`) need no restart, as the server reads them fresh on every request; reload the page to run them. `bun start` never restarts.

On first launch, choose a data folder. Pick a folder **outside this repo** (for example `~/Documents/board-data`). The app writes `todos.json`, `recipes.json` and `finance.json` there. On later visits, click **Reconnect** once to re-grant permission.

### Runners

`bun start` and `bun dev` also start the runners (`tools/worker.js`): a worker on this machine that does the board's background work on a schedule and saves what it finds in the data folder, whether or not a board tab is open. An open tab picks the results up within a few seconds, through the same disk sync that brings in another tab's saves. The worker stops with `bun start`; nothing keeps running once it exits, and nothing runs while the Mac sleeps (jobs that came due run once on wake).

The browser never tells the board where its data folder is on disk, so give the runners its path once in **Settings → Runners** (it is kept in `~/.config/board/worker.json`), or start the board with `BOARD_DATA=~/path/to/folder`. Settings → Runners lists each job with its last success, next run and last error, and lets you switch it off, change its interval or run it now. When the runners stop writing their heartbeat, a *Runners offline* badge shows in the top bar. Their API listens on `127.0.0.1:8420` (`WORKER_PORT` picks another) and answers only pages served from this machine. They log one line per job run, prefixed `worker`.

To look around first, click **Explore with sample data**. It opens the board on placeholder content kept in memory: nothing is written to disk, the automatic checks stay off, and a reload brings back the folder screen. It also works in Firefox and Safari.

## Data format

Every file has a `schemaVersion` field. Files are plain JSON and can be edited by hand. Reload the page after editing.

| File | Shape |
| --- | --- |
| `projects.json` | `{ projects: [{id, name, color, description, localPath, devCommand, devPreset, github: {org, repos: ['owner/repo']}, profile: {text, sources, updated, edited, usageId}, created}] }`. `localPath` is the project's folder on this machine, for Dev. `devCommand` is what a task's Dev button runs (empty: the default); `devPreset` is the id of a preset in `dev.json`, which runs instead when set. `github.org` and `github.repos` may be empty, for non-coding projects. `profile` is the project's saved Markdown profile, which the board's AI features read as context: `sources` are extra URLs it reads (blog, docs), `edited` is true once the text was changed by hand, and `usageId` points to the `usage.json` entry of the last build. A project without `profile` has none yet. |
| `todos.json` | `{ items: [{id, text, description, status, priority, category, projectId, due, auto, autoRef, inbox, email, issues, prs, devSession, created}], categories: [{id, name, color, scope, projectId, projectCategoryIds}], statuses: { <status>: {name, color, hidden} }, statusOrder: [<status>] }`. `projectId: null` means Personal. `due` is a `YYYY-MM-DD` deadline or empty. `auto` names what created the task (`domain`, `ssl`, `health`, `email`, `crawl`, `recurring`, `pools`, `telegram`, `cron`), `inbox: true` keeps it in To Organize, and `email: {id, dir}` links a task made from an Inbox email. `issues` and `prs` are `[{repo, number, url, title}]` (tasks saved earlier may have a single `issue` instead). `devSession` is the id of the Dev terminal last started on the task. `images` are `[{path, name, type}]`, `path` being the image's file in the data folder (`tasks/<task id>-<id>.png`). Array order is the display order (drag the grip to reorder). |
| `tools.json` | `{ sites: { <projectId>: { health, history, log, ssl, domain, dns, crawl, meta } }, every, providers: [{id, name, url, kind}], status: { <providerId>: {indicator, description, parts, components, incidents, maintenances, recent, recentCount, kind, at} } }`: the last result of each check, a site's `log` of warnings and errors (`{at, level, source, text}`), the minutes between automatic health and status checks, and the followed status pages. |
| `pools.json` | `{ cache: { "<chainId>:<v3\|v4>": {at, rows} }, prices: { <chainId>: {at, usd} }, scan: { <chainId>: { <wallet>: {node, from, to, span, ids, done} } } }`: the last good read of each chain and version, shown marked as outdated when a read fails; the last token prices; how far each v4 search got; and `fees: { <ref>: {at, f0, f1, v} }`, the unclaimed fees in tokens when the fee counter started (`v` marks a baseline taken since v3 fees are read in full; older v3 baselines start again); and `earned: { <ref>: { <unix hour>: [token0, token1] } }`, what each position earned from swaps per hour, in raw token units as text, for the last 31 days; and `collected: [{id, at, since, source, ref, pair, chain, tokenId, a0, a1, sym0, sym1, usd, note}]`, the fee collections (`source` is `chain`, `etherscan`, `auto` or `manual`; `level` ranks how sure a `chain` or `etherscan` reading is, 1 meaning its native coin part could not be read; `since` is the read before an `auto` one; `tx` is the collect transaction); `history: { <ref>: {node, from, to, span, done, events, checked} }`, how far each position's events were read and what they hold; `etherscan: { <chainId>: { <wallet>: {block, checked} } }`, how far each wallet's Etherscan history was read; and `hidden`, the `<ref>\|<tx>` keys of collections you removed, so they are not read again. `balances: { <chainId>: {at, rows} }` is the Wallets tab's last good read of each chain; `tokens: [{chainId, address, symbol, decimals}]` the tokens added by hand; `hiddenTokens` the `<chainId>:<address>` keys of hidden tokens. `lending: { <chainId>: {at, rows} }` is the Lending / Borrowing tab's last good read of each chain. Safe to delete except `collected`, `hidden`, `tokens` and `hiddenTokens`, which are not rebuilt; the rest is rebuilt by the next read. |
| `cron.json` | `{ flows: [{id, name, enabled, enabledAt, projectId, schedule: {every: 'interval'\|'daily'\|'days'\|'weekly'\|'monthly'\|'custom', minutes, from, to, time, times: ['HH:MM'], weekday, days: [0-6], day, monthDays: [1-31], months: [0-11], cron}, steps: [{id, type: 'gather'\|'ai'\|'stop'\|'task'\|'notify'\|'dev'\|'profile', ...}], lastRun, created}], runs: [{id, flowId, at, manual, dry, status: 'ok'\|'stopped'\|'error', error, steps: [{stepId, ok, output, note, ms}]}], templates: [{id, name, about, schedule, projectId, steps, created}], tests: { <flow id>: { <step id>: {ok, output, data, note, ms, at, nothing} } } }`. `templates` are flows saved as templates; their steps have no `id`. `tests` holds each step's last test result, so it shows in any browser on the folder; `data` is only saved when it is not the output read as JSON. `times` replaces the single `time`, `monthDays` the single `day` and `days` the single `weekday` of flows saved earlier, which still read; empty `months` means every month. `cron` is a five-field expression (minute, hour, day of the month, month, day of the week). `from` and `to` are an interval flow's active hours (empty: all day). `projectId` is the flow's project; a step's or source's own `projectId` overrides it, and empty follows the flow. A flow saved without `projectId` takes the one project its steps share. A `gather` step has `sources: [{id, source, label, projectId, url, text, count, flowId}]` and `append`; steps saved with one source on the step itself (`source`, `projectId`, `url`, `text`, `count`) still read. A `dev` step has `mode: 'claude'\|'command'`, `projectId`, `prompt` and `command`. A `profile` step has `projectId` and `keepEdited` (default true). A run's `dev` step also keeps `session` and `cwd`, the Dev terminal it started. A test run (`dry`) leaves `lastRun` alone. The last 60 runs are kept. |
| `dev.json` | `{ history: ['command'], runner, presets: [{id, name, command}] }`: the last 100 commands run in Dev, newest first, the runner's address when it is not the default, and the command presets set in Settings → Dev environment. |
| `inbox.json` | `{ emails: [{id, projectId, dir: 'sent'\|'received', from, to, cc, subject, at, status, taskId, unread, starred, archived, source, account, msgId}], syncedAt }`: the email list from Resend and Gmail (bodies are read when opened, not saved), up to 1000 per project. `status` is Resend's last event of a sent email. `taskId` is the task made from it. `unread`, `starred` and `archived` are kept on the board only; mail from a key's first read starts as read. Gmail rows have `source: 'gmail'`, the `account` address and Gmail's `msgId`, and keep up to 1000 per account; settings.json lists the accounts as `gmail: { accounts: [{email, projectId, labelId}] }`, both optional; `labelId` is a project label the Inbox filter can pick. Safe to delete except for those links. |
| `usage.json` | `{ entries: [{id, at, task, model, promptTokens, completionTokens, cost, input, output, meta, error}] }`: one entry per AI call. `input` is the messages sent (images and files as their type and size only) and `output` the reply; both are kept for the latest 300 calls. `meta` holds the duration, HTTP status, provider, served model, finish reason, generation id and the usage OpenRouter reported. `dev` holds what each task's claude session used, by worktree name: `{name, cwd, session, taskIds, added, sessions, models: { <model id>: {provider, input, output, thinking, cacheRead, cacheWrite, cost} }, cost, duration, apiDuration, linesAdded, linesRemoved, efforts: { <effort>: replies }, replies, start, end}` (times in ms; `cost` is null until claude has written its totals). |
| `settings.json` (blockchains) | `blockchains: { custom: [{id, name, rpc, explorer, symbol}], etherscan }`: chains added in Settings → Blockchains, and the Etherscan API key (a key saved before under `uniswap.etherscan` is still read). `rpc`, `node` and `explorer` hold one address or several, separated by spaces. The built-in chains keep their nodes, explorers and Liquidity Pools switch in `uniswap.chains: { <chainId>: {enabled, node, explorer} }`; an empty `node` or `explorer` uses the built-in ones. |
| `settings.json` (contracts) | `contracts: [{id, label, chainId, address, projectId, abi}]`: the contracts Tools and Monitoring read, each with its ABI as JSON. |
| `settings.json` (calendar) | `gcal: { accounts: [{email, projectId, labelId, calendars: [{id, name, color, on, projectId, labelId}]}] }`: the Google accounts Calendar reads and, per calendar, whether it is shown and its optional project and project label. An account's project and label apply to each of its calendars that has none of its own. Events are not saved here; the runners keep them in `calendar.json`. |
| `google.json` | `{ tokens: { "<gmail\|gcal>:<address>" or "web": {refresh, access, expiresAt, scope, at} }, pictures: { <address>: url } }`: every Google sign-in (Gmail and Calendar per account; `web` is Analytics and Search Console), with the refresh token the runners renew it with (Settings → Runners → Google sign-ins; a tab never renews one itself), so any browser profile that opens the folder is connected. A removed sign-in leaves `{removed: true, at}`. Also each account's picture. Keep it private: a refresh token reads that account's mail or calendar until you disconnect it or remove the board's access in your Google account. Deleting the file signs every account out. |
| `runners.json` | `{ worker: {pid, startedAt, beatAt, version, folderId}, jobs: { <job>: {lastRunAt, lastOkAt, nextRunAt, durationMs, ok, error, waiting, on, running, …counts} } }`: the runners' heartbeat, written only by them, every 30 s and after each job. A `beatAt` older than 90 s means they are not running. `folderId` is what they read from settings.json `folderId`, a random id the board writes once, so Settings can tell when they use another folder. settings.json `runners: { <job>: {every, on} }` holds each job's interval in minutes (empty: the default) and its switch. |
| `calendar.json` | `{ calendars: { "<address>\|<calendarId>": [{from, to, at, events}] } }`: the events the runners read, newest read first. Every 10 minutes they read each shown calendar from the start of last month to three months ahead; a page outside that range is read when Calendar shows it, and the last 6 such reads per calendar are kept. Home, Calendar and Cron read only this file. Safe to delete; it is read again. |
| `github.json` | `{ repos: { "owner/repo": {at, issues, prs, items: [{number, title, pr, updated, author, labels}], error} } }`: what the runners read of every project's repos every 15 minutes, the newest 30 open items each. Safe to delete. |
| `webstats.json` | `{ bing: { <website>: {at, traffic, queries, pages, error} } }`: Bing Webmaster's answers for each project website, read by the runners every 6 hours (the newest 3000 query and page rows). Monitoring adds them up for the range it shows. Safe to delete. |
| `fx.json` | `{ days: { "YYYY-MM-DD": {rate, date} }, source }`: the USD to CAD rate of each day Money needs, and the provider that answered last. A weekend or holiday keeps the `date` of the last published rate. settings.json `fx: {provider, fallback, manual}` holds the provider asked first, whether the others are asked when it fails, and a rate typed by hand. Safe to delete; rates are read again. |
| `notifications.json` | `{ items: [{id, kind, text, href, key, at, read}], prefs: { <kind>: {app, telegram} } }` |
| `recipes.json` | `{ recipes: [{id, title, status: 'idea'\|'testing'\|'final', tags, ingredients, steps, notes, images, source, scans, versions: [{id, date, changes, rating, notes}], created}] }` |
| `finance.json` | `{ entries: [{id, date, type: 'income'\|'expense', amount, category, note, created}], categories: [], budgets: { <category>: {amount, currency} } }`. A budget is per month and shows in the category breakdown when the period is one month. A category that goes over is listed on Home and announced once under the bell. |

Writes are debounced (about 300 ms) and serialized. The status pill in the top bar shows *Saving…*, *Saved* or *Save failed*. The board can be open in several tabs or browsers on the same folder: before writing a file, a tab merges in what another one saved to it (item by item, by `id`; when both changed the same field, the latest save wins), and every few seconds, and when it comes back into view, it reads the files again. A change not yet on disk is saved when the tab is hidden, and the browser asks before a reload or close would drop it. Nothing is kept in the browser's storage but the folder's handle.

The currency is set in `js/ui.js` (`CURRENCY`).

## Project layout

```
index.html            entry point
css/style.css         design tokens (light and dark) and layout
js/app.js             shell: folder connection, router, top nav
js/storage.js         File System Access API wrapper (read/write JSON, remember folder)
js/store.js           in-memory state, debounced saves merged with other tabs' saves, subscriptions
js/merge.js           three-way merge of a collection: last read, this tab, on disk
js/ui.js              h() DOM helper, ids, dates, money formatting
js/modules/index.js   registry of sections (the nav is built from this list)
js/modules/*.js       one file per section
```

## Adding a section

1. Create `js/modules/<name>.js` with the module contract:

   ```js
   import { h } from '../ui.js';

   export default {
     id: 'books',              // used in the URL hash: #/books
     title: 'Books',           // nav label
     icon: '📚',
     collection: 'books',      // writes books.json in the data folder
     defaults: { items: [] },  // shape used when the file does not exist yet
     render(root, store) {     // fill `root`; call store.update(...) to change data
       const { items } = store.get('books');
       root.replaceChildren(h('h2', null, `${items.length} books`));
     },
   };
   ```

2. Import it and add it to the array in `js/modules/index.js`.

Handlers should call `store.update(collection, mutate)` to save and re-render. Use `store.refresh()` for view-only state such as a filter or tab. Keep view state in a module-level object so it survives re-renders.
