# Board

A personal command center that runs locally. No backend, no build step, no dependencies: plain HTML, CSS and JavaScript modules. Your data is stored as JSON files in a folder you choose.

Sections (v1):

- **Todos**: personal and per-project lists. Type `buy milk #home` to file a todo under a project. Tasks are sorted by status (in progress first, completed last); click a column title to sort by it, and a third click returns to your own order. Drag the grip to reorder, within a status while sorted by status. Drop a task on the middle of another (a row, or a card on the board) to make it a subtask: subtasks show indented under their parent, and the arrow by the parent's title, with how many there are, folds them away. Drop a subtask above or below a top-level task to take it out. Drag one of several ticked tasks to move them all: under a task, next to one, into a board column or onto a project in the sidebar. Paste several lines to create a todo with a description. Click the description icon to read or edit it. While you write a description, a `/` lists Claude Code's skills under the cursor (the project's own, from its local folder, then yours, read through the command runner): keep typing to narrow the list, pick one with the arrows and Enter or Tab, and its `/name` is written. Paste or drop images on a task (or pick them with Add image in its details): they are kept in `tasks/` in the data folder, and a Dev session on the task hands them to claude. A task’s LinkedIn post (its details, or its right-click menu) opens a composer with the text under the task description’s “LinkedIn” heading (as Cron’s social post templates write it), or the whole description, an optional link and a feed preview; Save draft keeps it in `linkedin.json`, and Post now posts it as you through the runners (Settings → LinkedIn → Publish as you), then adds the post’s link to the task and marks it done. Schedule picks a day and time instead: the runners post it then (job “LinkedIn posts”, every minute), a task shows its post’s state as a pill, and a post more than 12 hours late (the Mac was asleep) is not posted but marked missed, with a notification.
- **Calendar**: the events of one or more Google accounts side by side, by day, week or month, coloured by calendar, with open task deadlines on their days. Day and week are a time grid as in Google Calendar: events placed by the hour and side by side when they overlap, all-day and multi-day events in a strip above, and a line at the current time; a small month beside it jumps to any day. Show or hide calendars from a searchable list of each account (with its Google picture) and its calendars, or filter by project or project label when a calendar has one (Settings → Google Calendar). Open an event for its time, place, notes and a link to Google, or turn it into a task in its calendar's project. A project and project label set on an account apply to each of its calendars without their own. Each account signs in on its own for about an hour. Each account connects once: its sign-in is kept in `google.json` in the data folder and renewed before it expires, so it stays connected in every browser profile that opens the folder. Events are cached in `google.json` too: a reload shows the last read at once, and Google is asked again once the cache is 10 minutes old, or with Refresh. Home shows the next two days. Posts scheduled or posted on LinkedIn from the board show as their own “LinkedIn posts” layer (a switch beside Task deadlines); a click opens the post to edit, reschedule, unschedule or post now.
- **Slack**: every Slack workspace you are signed in to, in one sidebar, so there is no switching between them. Sign in as yourself with the session of Slack's web client: paste the tokens that `copy(JSON.parse(localStorage.localConfig_v2).teams)` copies in app.slack.com's console, and the `d` cookie (no Slack app to install). Drag conversations into any order, gather channels of any workspace into groups, and tie a channel, a group or a whole workspace to a project; Projects shows the sidebar by project instead. Muting a conversation keeps it in place, dimmed and never counted as unread. Read messages with their files, links and reactions, post, reply in threads (also to the channel), react, and edit or delete your own. The open conversation and thread are read again every 5 seconds and unread counts every 20, through the runners; opening a conversation marks it read in Slack too.
- **Projects**: quick-add by name, or a detailed form for color, description, and GitHub links (one org, several repos, or none). A project can also be tied to an **npm** org (or user) and/or single packages (`my-package`, `@scope/my-package` or an npmjs.com link); its page lists them with their latest version, last publish and weekly downloads, read by the runners every hour (an org's first 60 packages). A project's **Local folder** (its path on this machine) is where the Dev section opens terminals for it; Browse finds it in a folder list starting at ~/Documents (needs the runner, see Dev). A project's **Profile** is a short saved text on what it is, its stack, how to work on it, its recent focus and what its website says: Build profile reads the local folder's README, AGENTS.md, CLAUDE.md, package.json and last 30 commits (through the runner), the repos on GitHub, and the website plus any extra URLs, then asks the model once (capped at about 6,000 words of input). A source that cannot be read is listed under Unknowns. The text can be edited by hand; Refresh asks before replacing edits. Tidy, Plan my day and Triage send the profiles of the projects in their input as context. A project's **Brand** keeps its images (logo, favicon, app icons, share image), colours as swatches (a click copies the value), fonts (shown in the font when this machine has it), style sheets and links, and notes. Images and links take a URL or a path in the local folder; local SVG files are shown through the runner. Add them by hand as `Label: value` lines, or with Find with AI: it reads the local folder through the runner (image files named like a logo or icon, the web manifest, Tailwind and theme configs, the custom properties and fonts of the main stylesheets, the icon tags of index.html) and the website's icon, theme colour, share image and stylesheet tags, asks the model once, and only adds what the brand does not hold yet, so nothing written by hand changes. A project's **Contacts** are the people tied to it: picture or initials, name, headline, company, LinkedIn profile, email addresses and notes. Add one by pasting a LinkedIn profile link (the name is guessed from the link), edit or delete it in its dialog, and tie it to several projects. Projects → ⋯ → Contacts lists every contact with a search. A contact saved twice (same LinkedIn profile or address) is merged. Inbox shows a contact's chip on an email from (or sent to) one of its addresses, and Calendar lists an event's guests, known ones as contacts and the others with **Add as contact**. A project’s **LinkedIn** block lists its posts as Drafts, Scheduled and Posted (with the latest reactions, comments, reposts and impressions when they have been read); New post opens the composer for the project, and each post can be edited, scheduled, posted now, deleted while a draft, or opened on LinkedIn once posted.
- **Kitchen**: recipe ideas, recipes you are testing, and final recipes. Log each iteration with notes and a rating. Drop a photo of a recipe, handwritten or printed (up to 4 pages), and the model set for Read recipe photos rewrites it as a recipe; the photo is kept in `recipes/` in the data folder.
- **Money**: rough income and expenses per month, with totals and a per-category breakdown.
- **Tools**: checks on each project's website: is it reachable (open a site for its response times, other checks and a log of warnings and errors), when its SSL certificate and domain expire, every DNS record it has (with SPF, DMARC and DKIM for mail), what its crawl files say (robots.txt, sitemap, llms.txt, security.txt, ads.txt, the web app manifest, app links and more, each previewed with a format check), and how a shared link to it looks, with a task for any tag that is missing or could be better. **Provider status** follows the status pages of the services you rely on (GitHub, Vercel, Cloudflare, OpenRouter, Resend, Slack, Gmail, Google Calendar, and any other Statuspage or Datadog page), with open incidents, maintenance and the last 30 days. **Contracts** reads and writes the smart contracts saved in Settings: every view function can be called with typed inputs (arrays and tuples as JSON) and shows its decoded answer, **Read all** reads the ones without inputs, and every other function is sent as a transaction through your browser wallet once you press **Connect wallet** (nothing asks the wallet before that; with several wallet extensions installed, such as MetaMask, Rabby, Coinbase Wallet or Brave Wallet, pick one from the list), which switches to the contract's chain and asks before signing; the board then waits for it to land. **Requests** is a small Postman: pick a method, type a URL, add query params, headers, a body (JSON, GraphQL, text or form fields) and Bearer or Basic auth, then **Send** (Cmd/Ctrl+Enter from any field; Cmd/Ctrl+S saves). A GraphQL body takes a query and its variables; **Read the schema** lists the API's queries and mutations, and picking one starts a query from it. Pasting a cURL command into the URL field imports it. The answer shows its status, time, size, headers and body, with JSON indented and coloured (**Raw** shows it as it came). Save a request to keep it under a project; **Copy as cURL** and **Import cURL** convert both ways. The runners send it (`bun start`), so CORS never blocks it; without them the browser sends it, and a site that does not allow other sites' requests cannot be read.
- **Summary** (the first view of the **DeFi** tab): total liquidity across the other views (wallet balances, LP positions, unclaimed fees, and Aave supplied less borrowed) with each one's share, warnings for Aave accounts close to liquidation and LP positions out of range (in the pills at the right of the DeFi tabs, as every DeFi view's alerts and notes are: a pill per kind with its count, opening the list), the fees collected over 30 days, and the main lines of Wallets, LP Positions and Lending / Borrowing, each with a link to open it. **Refresh all** reads them all again. It reads nothing of its own.
- **Liquidity Pools** (the **DeFi** tab, with **LP Positions** and **LP Fees Collected** views): Uniswap v2, v3 and v4 positions of the wallets you add in Settings → Wallets, on Ethereum, Base, Arbitrum One, Optimism, Polygon, BNB Chain, Avalanche, Unichain, Robinhood Chain and ZKsync Era (v3 only, as Uniswap has no v2 or v4 there): range, value, unclaimed fees, fee APR and token split. A v2 position is a wallet's share of a pair over the full range: its value is that share of the pair's reserves, its fees stay in the pool (so it has no unclaimed fees and no collects), and its fee APR comes from the pair's swaps. A chain cannot list the v2 pairs a wallet holds, so they are found from Etherscan's list of the tokens the wallet received when its key is set, and otherwise added with **Add position** by link or pair address, which reads the pair for every wallet. PancakeSwap v2 and v3 positions are read the same way on Ethereum, BNB Chain, Arbitrum One, Base, Robinhood Chain and ZKsync Era, marked with a PancakeSwap pill. Positions staked in PancakeSwap's farm (MasterChef v3) are found with the others, marked **Farming**, with the CAKE they can harvest next to the unclaimed fees. Fee APR counts only what liquidity keeps: each PancakeSwap pool gives part of every fee to the protocol (a third on BNB Chain's, 12% elsewhere today), and PancakeSwap v2 keeps 0.17% of its 0.25%. Add position takes pancakeswap.finance position links, or a number or pair address with PancakeSwap picked. Positions are sorted by value, unclaimed fees, fee APR, movement, newest or oldest. In the list view, every column header sorts by that column; click again to flip the order. Fee APR is read over the window picked beside Sort (15 min, 1 h, 3 h, 6 h, 24 h, 7 d or 30 d): every swap in the pool that ended inside the position's range pays it the fee times its share of the liquidity, as a yearly rate of its value. It is an estimate. Public nodes keep about a day of swap history, so the board also saves each position's earnings per hour, and the 7 and 30 day windows fill in as long as the board is opened about once a day. A window that is only partly covered shows the time it covers next to the rate. Where swaps cannot be read, fee APR counts the fees earned since the board first read the position, and shows after an hour. **Movement**, on each card and in the list, is the change in fee APR from the window before the one picked (the 24 h before the last 24 h, for example), in percentage points, shown once both windows are at least half covered. The **⇄** button beside a price range shows it in the pair's other token; the choice is saved per pair and used wherever that pair shows. Click a card, a row or a position in Fees Collected, open or closed, to open its detail: the range on a wider price scale with where the price sits, the room to each edge and the range width; holdings and unclaimed fees per token; fees earned and the fee APR they make over the last 24 h, 7 and 30 days from the saved hours, and per day; its collections; and its wallet, pool, token addresses (with block explorer links), liquidity and collect search. A position whose wallet was removed shows its last saved read. Read-only: only public addresses are used. v4 positions cannot be listed with a call, so the board finds them by searching each wallet's history on the chain, and remembers how far it got. Most public nodes keep only recent history, so set a node that keeps full history, or use **Add position** on the tab: paste a position link from app.uniswap.org (its chain and version are read from the link, for example `/positions/v3/base/556505`), or type its number and pick its chain and version. That also adds a v3 position held by an address that is not in your wallets. Each chain shows as soon as it is read. When a chain cannot be read, its last good read is shown and marked as outdated. Positions your wallets still hold but have emptied (no liquidity, no unclaimed fees) show under the **Closed** filter, left out of the totals. **LP Fees Collected** logs each collection, read from the collect transaction itself: the tokens it paid the wallet, less any liquidity removed in it (for v4, worked out at the pool's price just before), at the token prices of that day. The native coin leaves no token transfer, so its part is what the wallet gained in it, plus the gas it paid, or the amount Etherscan traced. Collects are found three ways, and the surest reading of each is kept: from the node, v3 positions' own events and v4's pool manager events, which read new blocks on every load and walk back toward each position's opening while the node keeps the blocks; and, with an optional Etherscan API key in Settings → Blockchains, each wallet's transactions to the Uniswap position managers, back to its first one. Etherscan only logs positions the board shows, as a burned position no longer says what its tokens are. Between two reads, a drop in a position's unclaimed fees is logged too, as a floor, and gives way to a reading of the same collect from the chain. You can also log a collection by hand or remove one. It shows the total collected, the average per day, week, month and year over all time, 30 days, 90 days or a year, and a chart by day, week or month whose bars show their total, count and top positions on hover, tap or arrow keys. Below the chart: an **Outlook** row (the range against the one before it, month-end and year-end estimates at the last 30 days' pace, the days to the next round total, the time since the last collect with the usual gap, and the average and largest collect); a **running total** with a dashed estimate ahead at the range's pace; the **pace per day** as 7-day and 30-day rolling averages, saying whether fees are speeding up or slowing down; **where fees came from** by position, chain or source, with each one's share; and a calendar of the **last 26 weeks**, one square per day, shaded by the fees collected, with the weekday that brings the most. They follow the chain, token and source filters. The token filter is searchable and shows each token's logo; each position in the log has a dot for open (green in range, amber out of range), closed (grey) or no longer read (hollow). **Search coverage** starts collapsed to a one-line recap and opens to say how sure the log is to hold every collect, for all chains and per chain: the share of positions, open and closed, whose search reached the transaction that opened them, or whose wallet Etherscan has read in full, with partial credit for the blocks searched back so far. Each load searches a step further back. With several nodes on a chain, its positions are searched side by side, one per node, and a position searches several block ranges at once when there are more nodes than positions, so each load reaches further; a line per position says what is being searched. **Search further** beside a chain runs one more step for that chain right away. **AI insights**, above the positions, counts how many are in range, out of range (with the value sitting idle) and near an edge, and with an OpenRouter key asks the model set for Pool insights in Settings to read them: a short summary, then one action per position (keep, watch, re-center, widen, narrow, collect fees or withdraw) with the reason and, where it fits, a suggested range. Prices are read and shown in the base each pair is shown in (see **⇄**). The last 5 reads are saved with their date and time and open again from tabs, and each can be filtered by action, in or out of range, and chain. It reads only the numbers the board shows, and is not financial advice.
- **Wallets** (in the **DeFi** tab): what each wallet in Settings → Wallets holds on the chains Liquidity Pools reads: its native coin and every token on the chain's Uniswap token list, read in a few batched calls through Multicall3, with prices from DefiLlama. Shows the total, the value by token, by chain and by wallet, and a sortable table filtered by wallet and chain. Hide a token from its row; **Tokens** adds a token the list does not carry by its contract address, and lists the added and hidden ones. Each chain shows as soon as it is read; a chain that fails keeps showing its last read. Read-only.
- **Lending / Borrowing** (in the **DeFi** tab): the Aave v3 positions of every wallet in Settings → Wallets, on the chains read that have Aave (Ethereum, Base, Arbitrum One, Optimism, Polygon, BNB Chain, Avalanche and ZKsync Era). One card per wallet and chain, riskiest first: the health factor (green, amber under 1.5, red under 1.1, where liquidation starts below 1), what is supplied and borrowed with each asset's APY and whether it counts as collateral, the net value and net APY, and how much of the borrow limit is used. Totals across all of them, the lowest health factor, and a warning for any account under 1.1. Filter by wallet and chain, and switch between cards and a list with one row per account. Values use Aave's own price oracle. Read-only.
- **Dev**: a small IDE for this machine, Cursor style. Pick a workspace (the board's folder, your home folder, or a project's local folder): its files show as a tree on the left (without `.git`, `node_modules` and build caches), and a file opens read-only in a tab, with line numbers and syntax colours for JavaScript, TypeScript, JSON, CSS, HTML, Markdown, Python, Shell, YAML, TOML, SQL, Solidity, Rust, Go, C, Java and Swift (files up to 1 MB). Terminals sit below: each runs commands in a real terminal (a pseudo-terminal from the system's `script` tool), so colours show (adapted to the light or dark theme, so a program's own colours stay readable) and interactive programs work, including the Claude CLI, prompts and full-screen tools like `vi`: click the output and type, and your keys go to the program. `cd` moves the terminal, `clear` or Ctrl+L empties it, a web link it prints (plain or OSC 8) opens in a new tab when clicked, Up and Down walk the saved commands, and Stop ends the command and anything it started. Hover a folder in the tree to open a terminal there. Paste or drop an image on a running terminal and its path is typed in, so claude attaches it (the runner saves a copy in its state folder; images not used for 30 days are deleted). Icons at the top of the side panel switch between Files, **Search**, **Source control** (with a badge counting changed files) and **Worktrees**, as in VS Code or Cursor; each panel has a title with its actions beside it, and its right edge drags to make it wider or narrower (a double click resets it; each browser remembers the width), and the Files tree hides the worktrees claude makes in `.claude/worktrees`. Search finds text in the workspace's files as you type (through `git grep`, so files git ignores, binary files and claude's worktrees are left out), with toggles for match case, whole word and regular expression, and, under the `…` button, files to include and exclude (comma-separated globs such as `*.js, src/`). Results are grouped by file; a match opens the file at its line. It shows the first 2,000 matches. Source control leaves out the worktrees claude makes in `.claude/worktrees`, and Commit all does not stage them. It shows the workspace's branch (click it to switch to another or create one), pull and push with how many commits each way (Publish for a branch with no upstream, plus fetch), a commit box (Cmd/Ctrl+Enter commits; with nothing staged, Commit all stages every change first), and the merge conflicts, staged changes and changes, each file with buttons to stage, unstage, discard (after a confirmation) or open it. A file opens its diff in an editor tab, and a recent commit opens what it changed. The pull request button in its title opens the branch as a pull request in an editor tab, as GitHub's Files changed shows it: everything it changes against the default branch since they parted (uncommitted and new files too, unless you untick them), with the branches, commits and lines added and removed, the changed files listed on the left, and each file's diff as a card that folds. Ticking Viewed folds a file and stays ticked in this browser until the file changes again; diffs over 1,500 lines start folded. The file tree colours changed files with git's letter (M, U, A, D) and marks the folders holding them. Source control reads the repository again every few seconds while Dev is drawn, and after each command ends. Pull only fast-forwards, and git never asks for a password here: a push that needs one fails and says so. Worktrees lists every git worktree of the workspace's repository but the main checkout, each with a dot: green while claude (its lock) or a terminal's command runs in it, amber while an open task or terminal points at it, grey when nothing uses it. They are grouped under In use, Held and Not in use (each group folds), and under each name are the task it was made for, its branch and what uses it. Each can be removed, or all the unused ones, or all of them (after a confirmation); git keeps any with changes or untracked files and says why beside it, and branches are kept. Up to 50 terminals run side by side (`TERMINAL_MAX` changes the limit); past 25, the Terminals panel suggests closing the idle and finished ones and those of tasks done or in review, with a Clean up button. Terminals outlive the page: reloading or closing it leaves their commands running, and when Dev opens again every terminal is back with its whole output (the last 2 MB of each). The runner, not the browser, keeps the list of open terminals and numbers them, so another browser on this machine (or one whose site data was cleared) shows the same terminals under the same numbers; a terminal opened or closed in one browser shows up or goes away in the other within a couple of seconds, and each browser keeps its own terminal shown. With more than one terminal open, the address names the one shown (`#/dev?term=2`), so a refresh or a bookmark opens it. The runner keeps that output in a folder of the system's temp folder (`TERMINAL_STATE` picks another), so it also survives a runner restart, though a command running then is stopped; terminals not opened for 30 days are deleted. The bar above the output names the terminal shown (a click opens the Terminals panel, which lists them all). Each terminal's dot says where it stands: blue and flashing while claude works, purple and flashing fast when it asks a question, a plan's approval or a permission, amber when its turn ended and it waits for you, green once done, red when it ended with an error (flashing red when claude gave no sign for 5 minutes), grey and flashing for any other running command, faded grey when idle. For claude, a turns button beside it counts the prompts of its session, read from its transcript, with a dot for the last one: green while claude works, accent while it waits for you; a click opens a panel with every turn, newest first: its prompt, when it was sent and how long it took, split into the time claude worked and the time it waited on you (a question it asked, its plan to approve, or a permission while it waits), drawn as a bar of green working and accent waiting stretches, with the totals and the question it waits on at the top. The turn still going counts up live (a click on a turn copies its prompt). A subagents button beside it counts the subagents that claude started (working ones over all of them, with a green dot while any works, read from the transcripts claude keeps beside its own); a click lists them, newest first: each one's task, type, whether it runs in the background, when it started, how long it ran and how many tools it called, with what it is doing now (its last tool call and what it works on) or, once done, the start of its answer. A click on one unfolds its whole task and its last text. A tools button (a wrench) counts the tool calls of the session, its subagents' own included; a click opens a summary of the tools used: the calls that succeeded and failed and the time they took, how many claude made and how many its subagents, the tools used most, the one that took the most time and the one that failed most, then every tool, the most called first (Bash, Edit, Read, subagents, MCP by server): its calls and share of them as a bar, with the failed calls in red, how many its subagents made, and its time per call. A click on a tool with failed calls unfolds them, newest first: when each was called, what it was given (the command, file or address), the error it got back, and the subagent that made it; the last 60 are kept. Closing a terminal stops its command and deletes its output. Needs `bun start` (or `bun dev`), which starts the runner (`tools/terminal.js`); it listens on 127.0.0.1 only, answers only pages served from this machine, and reads your files without ever writing one, except through the git actions you click in Source control and Worktrees and the images you hand it. macOS and Linux; on Windows commands run without a terminal.
- **Dev sessions file their own subtasks**: a claude session started on a task can list, add and edit that task's subtasks with `node "$BOARD_CLI" task list|show|add|edit` (`tools/board.js`, through the runners). It reaches only the task it was started for (read-only), what is under it and what it made, 100 tasks at most; anything else is refused. Its tasks show a **Dev** badge that opens its terminal. It can also see the other terminals on the same tasks (`session`: their worktree, branch, last commit), read its task's project and brand (`project`, `brand --css`), and read or attach a task's images (`image list|get|add`, image types only, 5 MB at most), all limited to its own tasks. Install the `board-tasks` skill once (Settings → Coding Agents, or `bun run install-skill` from the checkout the board runs from) so claude knows how; a line in the session's system prompt points it there.
- **Cron**: recurring flows, drawn as a chain of steps like a workflow canvas. A schedule (every few minutes or hours within optional active hours, daily, on chosen days of the week such as weekdays, or on chosen days of the month and months, each at one or more times of day, or a custom cron expression such as `*/15 9-17 * * mon-fri` with a preview of its next runs) starts the chain: gather data from the board (open, overdue, high priority or soon-due tasks, one project or an overview of all, spending this or last month, income, calendar events today or in the next 7 days, upcoming meetings with guests (events starting within the next 2 hours, or any number, that have a guest besides you, each guest with what Contacts knows of them and the subjects and dates of the latest Inbox emails with them; its list feeds a Loop or Filter duplicates step), unread Inbox mail, unread notifications, site check problems, liquidity pool positions, LinkedIn over the last 7 days (or any number of days: each account's followers and their change, the posts published with their last read results and the best and worst of them, the scheduled posts next, the drafts waiting and the new comments, for every account or one project's), a web page such as a project's website, a path on it like `/blog` or any full link, along with up to 10 pages of the same site it links to, picked across its sections, such as a blog's latest posts, the flow's own past outputs, another flow's latest output, or fixed text; the source list is searchable, one data step can read several sources, each under a heading with an optional label), ask an AI model with a prompt that uses `{{input}}`, then create a task (its title and description take variables, the description being the input by default; its output is the new task's id, so a later Create task step can put its task under it with Parent task `{{step2}}`), update a task by its id (an "Update task" step adds a note below its description, or in its place, and can change its title, status, priority or due date; `{{step2}}` names the task an earlier step made, and a Run in Dev step after it works on that task) or post a notification, or start work in Dev: a "Run in Dev" step hands a Dev prompt to the project's Dev command, a preset from Settings → Coding Agents or a custom command (or runs a plain shell command) in a new Dev terminal in a project's local folder, without leaving the page, and the task made earlier in the run goes with it, as from its Dev button, so the PRs claude opens are added to it. Once claude is done in its worktree, the run sends it `/exit` and answers its question with Remove worktree, but only when nothing would be lost: no uncommitted file and every commit on a remote. Otherwise it picks Keep, so the worktree and its branch stay. A data step can add to the previous one's output instead of replacing it, so one prompt can hold a website, its blog and earlier drafts. Templates cover website content ideas, blog post drafts, X and LinkedIn posts for a project or a personal account, and a weekly LinkedIn summary (Mondays at 09:00: the week's numbers and what worked, as a notification, and a task "Next LinkedIn post: …" with a draft); they write drafts as tasks and never post anything. "Find people at a company" uses the LinkedIn session (about 5 calls, none when cached): from a company name, title keywords and the roles wanted, written in its first step, it finds the company, lists its people, keeps those an AI filter says fit the roles, saves them to Contacts (merged, so a run again adds no duplicate) and adds a task "People at …" listing each as `- [name](profile) — headline (the model's reason)`. "Meeting prep" runs every 30 minutes from 08:00 to 19:00: it finds the meetings with guests in the next 2 hours, drops those already prepared (Filter duplicates on the meeting's title and time), and for each one asks the model for a short brief (who the guests are, the last exchanges, open points, questions to ask; its instructions are the "Meeting prep" prompt in Settings → Prompts) and adds it as a task due today in the calendar's project. A task step's project can be a variable such as `{{item.projectId}}`. "Blog post as a PR" drafts a post, adds it as a task, then has claude add it to the project's repository and open a pull request. A "Stop if" step ends the run quietly, for example when the data step found nothing. A "Format" step reshapes its input into cleaner output: text from a template, one line per item of a list (`- {{item.title}}`, joined by new lines, blank lines, commas or spaces), or named JSON fields (a value that is a single variable, such as `{{step2.items}}`, stays whole). A "Parse JSON" step reads the JSON out of a text that is not only JSON, such as a model's or claude's answer: a code fence, prose around it, lines a terminal wrapped, or a copy cut off at either end, of which it keeps the whole parts (the items of a list, without the one cut in half); with several JSON values it keeps the largest, the last, the first or all of them, and later steps read it as `{{stepN}}` and `{{stepN[0].title}}`. A "Filter duplicates" step keeps the items of a list that no task has yet, so a daily flow that finds the same job posts or articles makes a task only for the new ones: each item gives a key (`{{item.url}}`, or the title the task will get), a task matches when its title is the key or its title or description holds it, done tasks count, it compares with the tasks this flow made, the flow's project or every task, two items with the same key keep the first, and an empty result lets "Stop if" end the run. An "AI filter" step asks a model which items of a list (a JSON list, or one item per line) fit a criterion written in words, such as "people who decide on engineering hires", and either keeps those that match, in their order, or ranks them and keeps the top N by score: it sends 20 items per call, one call after the other (200 items at most), each item as a template such as `{{item.name}} — {{item.headline}}` or else as JSON, on the step's model or Cron's default, with its system prompt in Settings → Prompts; its output is the kept items as they were, each JSON item with the model's `_reason` and `_score` added (`{{stepN[0].name}}`, `{{item._reason}}` in a loop after it), a call that fails or gives no JSON is tried once more and then fails the step, as an AI generate step does, an item the model skipped is left out (scored 0 when ranking) and the note says how many, and an empty result lets "Stop if" end the run. LinkedIn steps (grouped as LinkedIn in the palette) read through the saved session's queue (see Settings → LinkedIn and Outside services), each showing how many calls it may spend against today's limit; answers are cached for a week, so running or testing a step again with the same inputs spends no call, and the session's errors read plainly (no session saved, today's limit reached so a scheduled run tries again tomorrow, or signed out so the cookies need saving again). "LinkedIn: find company" takes a name (`{{item.company}}`) and gives a list of companies with `name`, `handle` (`company/<name>`), `url`, `urn`, `id`, `industry`, `size`, `followers`, `website` and `headquarters`: the best match as a one-item list with its page's details (2 calls), or the top N matches as the search gives them (1 call), so a later step reads `{{stepN[0].id}}`. "LinkedIn: company people" takes a company (an id from find company, its page link, or a name it looks up first), optional title keywords and location text (matched on each result), and how many (20 by default, at most 100; 10 per call, stopping at a short page); it gives `name`, `headline`, `location`, `url`, `handle`, `degree`, `image` and `company` per person, and skips the "LinkedIn Member" results LinkedIn hides from out-of-network accounts unless told to keep them (then `hidden: true`); LinkedIn caps people searches each month for free accounts. "LinkedIn: profile" reads one member by handle or link (1 call): `name`, `headline`, `location`, `about`, `currentTitle`, `currentCompany`, `experience` (up to 5 lines), `url` and `handle`. "Save contacts" saves a list's people to Contacts (name, headline, a company template such as `{{item.company}}`, LinkedIn handle, email, location, picture) in the flow's project or a chosen one, merged with those already there by LinkedIn handle or address, and gives `{ added, updated, contacts }`; a test of that step only says what it would save. A "Loop over items" step, as in n8n, runs the next steps once for each item of a list (a JSON list, or one item per line of text, 20 items by default and at most 200): in them `{{item}}`, `{{item.title}}`, `{{index}}` and `{{count}}` read the item, a "Stop if" skips the rest for that item only, and after the loop each repeated step reads as the list of what it gave for every item. A "Refresh project profile" step rebuilds a project's profile as Refresh does in Projects (its output is the new profile), and a profile edited by hand never blocks it: by default the model updates it and keeps the edits (the step can also replace it or leave it as it is, and the run goes on); the "Refresh project profile" template does it every Monday. "Test run" tries the whole flow as it will run: it makes its tasks and starts its Dev terminals, tied together as from a task's Dev button, but sends no notification, leaves the schedule alone and is not read back as the flow's history. A "Run in Dev" step with steps after it waits for its terminal (until it ends, or claude is done and waits), then passes on what it did: `{{input}}` as text, and its parts as `{{stepN.branch}}`, `{{stepN.commit}}`, `{{stepN.files}}`, `{{stepN.pr.url}}`, `{{stepN.answer}}` (claude's final answer, read from its transcript), `{{stepN.written}}` (the files claude wrote, wherever they are) and `{{stepN.output}}`, so a second Run in Dev, an AI step or a notification can build on it; when another Run in Dev follows, a checkbox adds “Output format: Output the final output in valid JSON” to its prompt, and the JSON its output ends with is read back as `{{stepN.json}}` (and its keys, such as `{{stepN.json.title}}`); the PR it opened is added to the run's task. A "Run in Dev" step can also be tested "in a terminal": it starts for real (with no task) and its output shows under the step as it runs; a test still waiting when the page reloads is picked up again, and finishes once claude is done. Each run's Dev terminal can be read later under that step in the run, from what the runner keeps until the terminal is closed in Dev, and "Open in Dev" opens it to type in it. Each step can also be tested on its own, as in n8n: the steps before it that have no test data run first, and its input and output show as JSON trees. ## Run it

Browsers only allow the folder picker on a secure origin, so serve the folder locally:

```sh
bun start
# or, without Bun
node tools/start.js
```

This starts the board's static server, the Dev section's command runner and the runners (see below) together, in one process; Ctrl+C stops them all. Each prints its own lines in the terminal, prefixed with its name (`board`, `terminal`, `worker`): the board logs page loads and failed requests, and the runners one line per job run. Then open `http://localhost:8000` in **Chrome or Edge**. `PORT=<port>` picks another port for the board, and `TERMINAL_PORT` for the runner (8419; set the same address on the Dev page). To run only one part, use `bun run serve` or `bun run terminal`. `package.json` only holds these scripts: there is nothing to install. The File System Access API is not available in Firefox or Safari.

`tools/serve.js` has no dependencies and marks every file `no-cache`, so the browser always runs the code you just edited. Any other static server works too, but `python3 -m http.server` sends no cache headers, so Chrome reuses the modules it cached earlier and keeps running the old code after a reload: with that server, hard reload the page (Cmd+Shift+R) after every change.

While working on the board itself, run `bun dev` instead of `bun start`: it starts the same services and restarts the static server and the runners when a file under `tools/` changes. The terminal runner is never restarted, so a pull that changes `tools/` leaves Dev's terminals and their claude sessions running; restart `bun dev` yourself after changing `tools/terminal.js`. The page's own files (`index.html`, `js/`, `css/`) need no restart, as the server reads them fresh on every request; reload the page to run them. `bun start` never restarts.

On first launch, choose a data folder. Pick a folder **outside this repo** (for example `~/Documents/board-data`). The app writes `todos.json`, `recipes.json` and `finance.json` there. On later visits, click **Reconnect** once to re-grant permission.

### Runners

`bun start` and `bun dev` also start the runners (`tools/worker.js`): a worker on this machine that does the board's background work on a schedule and saves what it finds in the data folder, whether or not a board tab is open. An open tab picks the results up within a few seconds, through the same disk sync that brings in another tab's saves. The worker stops with `bun start`; nothing keeps running once it exits, and nothing runs while the Mac sleeps (jobs that came due run once on wake).

The browser never tells the board where its data folder is on disk. When the runners have no folder yet, an open tab asks them to look for it by name in your home folder, Desktop, Documents, Downloads and iCloud Drive (and one level below those), and they use it when exactly one folder's `settings.json` has the tab's `folderId`. Otherwise give its path, or pick it with Browse, in **Settings → Runners** (it is kept in `~/.config/board/worker.json`), or start the board with `BOARD_DATA=~/path/to/folder`. Settings → Runners lists each job with its last success, next run and last error, and lets you switch it off, change its interval or run it now. When the runners stop writing their heartbeat, a *Runners offline* badge shows in the top bar. Their API listens on `127.0.0.1:8420` (`WORKER_PORT` picks another) and answers only pages served from this machine. They log one line per job run, prefixed `worker`.

To look around first, click **Explore with sample data**. It opens the board on placeholder content kept in memory: nothing is written to disk, the automatic checks stay off, and a reload brings back the folder screen. It also works in Firefox and Safari.

Writes are debounced (about 300 ms) and serialized. A save icon shows in the top bar only while a change is not on disk: orange while saving, red when a save failed (hover it for the reason). The board can be open in several tabs or browsers on the same folder: before writing a file, a tab merges in what another one saved to it (item by item, by `id`; when both changed the same field, the latest save wins), and every few seconds, and when it comes back into view, it reads the files again. A change not yet on disk is saved when the tab is hidden, and the browser asks before a reload or close would drop it. Nothing is kept in the browser's storage but the folder's handle.

## Project layout

```
index.html            entry point
css/style.css         design tokens (light and dark) and layout
js/app.js             shell: folder connection, router, top nav
js/storage.js         File System Access API wrapper (read/write JSON, remember folder)
js/store.js           in-memory state, debounced saves merged with other tabs' saves, subscriptions
js/merge.js           three-way merge of a collection: last read, this tab, on disk
js/ui.js              h() DOM helper, ids, dates, money formatting
js/modules/index.js   registry of sections (the nav is built from this list)
js/modules/*.js       one file per section
```

## Adding a section

1. Create `js/modules/<name>.js` with the module contract:

   ```js
   import { h } from '../ui.js';

   export default {
     id: 'books',              // used in the URL hash: #/books
     title: 'Books',           // nav label
     icon: '📚',
     collection: 'books',      // writes books.json in the data folder
     defaults: { items: [] },  // shape used when the file does not exist yet
     render(root, store) {     // fill `root`; call store.update(...) to change data
       const { items } = store.get('books');
       root.replaceChildren(h('h2', null, `${items.length} books`));
     },
   };
   ```

2. Import it and add it to the array in `js/modules/index.js`.

Handlers should call `store.update(collection, mutate)` to save and re-render. Use `store.refresh()` for view-only state such as a filter or tab. Keep view state in a module-level object so it survives re-renders.
